# Decisions Log

Append-only log of non-trivial decisions made on this project. Entries are not edited in place — if a decision is reversed, a new entry records the reversal and references the original.

## What belongs here

- Decisions with irreversible or cross-cutting consequences
- Trade-offs that took meaningful discussion
- Scope changes, gate bypasses, and deferred items
- Stage closures (Gate 1, Gate 2, Gate 3, Gate 4, Close)
- Retrospective entries at day 14 post-launch

## What does not belong here

- Transient implementation notes → stage `build-notes.md`
- Bugs → `stages/04-review/output/punch-list.md`
- Design exploration → `stages/02-design/claude-design/` or `./figma/`

## Entry format

```
## YYYY-MM-DD — [short title]
**Stage:** [01-brief | 02-design | 03-build | 04-review | 05-launch]
**Type:** [Stack / tech choice | UX / design tradeoff | Architecture | Product / scope call]
**Status:** [proposed | accepted | superseded by <date-title> | reversed]

**Context.** What situation forced the decision. Include relevant constraints — timeline, prior decisions, what would happen if no choice were made.
**Decision.** What was chosen. One sentence, starting with a verb.
**Rationale.** Why — the reasoning behind the choice.
**Alternatives considered.** What else was on the table and why it was ruled out. At least one alternative; if only one option existed, say so.
**Consequences.** Easier: what this simplifies or de-risks. Harder: what this constrains or makes more expensive to change.
```

## 2026-07-10 — Meta Graph API access: System User token over Instagram Login
**Stage:** 03-build
**Type:** Architecture
**Status:** accepted

**Context.** The existing Social Playbook tab (`megs-playbook`) showed static best-practice text with no real account stats — Instagram/Facebook block unauthenticated scraping, so live post-performance data requires an authenticated Graph API path. Meghan's Instagram (`@meghanclarissecave`) is linked to her "Meghan Clarisse Music" Facebook Page inside her Meta Business Portfolio ("Meghan"). Two credential paths were available: a Meta Business System User token, or an Instagram-Login (Instagram API with Instagram Login) user token tied to a logged-in Instagram account.
**Decision.** Use a Meta Business System User (`megcmusic-automation`, Full access to both the Page and the Instagram account) with a long-lived System User access token, stored as `META_SYSTEM_USER_TOKEN` in Vercel (Production + Preview).
**Rationale.** A System User token is designed for exactly this shape of integration — unattended, server-side, no human session to expire or re-authenticate. It's scoped to the business portfolio rather than a personal login, doesn't depend on Meghan's own Instagram session staying valid, and survives password/device changes on her end. The Instagram-Login path would have tied the integration to a personal account session with a shorter natural lifespan and no clean way to scope permissions to just the automation's needs.
**Alternatives considered.** Instagram API with Instagram Login (user-token path) — rejected: ties the credential to a personal login session rather than a business-scoped service identity, more fragile for an unattended Vercel cron job.
**Consequences.** Easier: token is decoupled from any individual's login state, permissions are explicitly scoped (`instagram_basic`, `instagram_manage_insights`, `pages_read_engagement`, `pages_show_list`), regeneration doesn't require Meghan's involvement. Harder: requires maintaining a Meta Developer app (`Business`, App ID `1020080587391692`) and system user in Business Settings as ongoing infrastructure; a second, orphaned "Business" app (App ID `3187283798124578`, Business: None) was created by accident mid-setup and should be deleted once the real one is confirmed stable, to avoid future mix-ups. Verified end-to-end 2026-07-10: `me/accounts` resolved Page ID `108048260606098` → Instagram Business Account ID `17841401582839394`, and a live `insights?metric=reach&period=day` call returned real data. The token used during that verification was pasted in a chat transcript (via Graph API paging URLs) and was rotated immediately after — the token now live in Vercel is a fresh regeneration, not the one exposed during testing.

## 2026-06-16 — Web fonts via Google Fonts @import
**Stage:** 01-brief
**Type:** Stack / tech choice
**Status:** accepted

**Context.** The brand type system — Lora, Open Sans, Praise, Newsreader — must load on every surface from scaffold onward. Studio learnings prefer self-hosting display faces (`self-host-variable-font-axes`, `font-display-optional`) to avoid the visible late-swap re-render.

**Consequences.** Easier: type system correct immediately; no font files to manage now. Harder: a render-blocking CDN `@import` and possible swap flash remain until the Gate 3 self-host pass; must be revisited before launch.

## 2026-06-16 — Bound Events API calls so a slow upstream can't fail the ISR build
**Stage:** 03-build
**Type:** Architecture
**Status:** accepted

**Context.** The first Vercel preview build prerendered `/` (now fetching events) and timed out — "took more than 60 seconds", three attempts, then failed. The API answers in <1s from a normal network and at every page size, so query cost is not the issue; the Vercel build region intermittently cannot reach `megcmusic.com` and the fetch hangs to the 60s static-generation wall. **Alternatives considered.** (1) `force-dynamic` — rejected: drops ISR (WORKSPACE: ISR only). (2) Reduce `per_page` — rejected: the API is fast at all sizes; size is not the cost. (3) Raise the timeout only — rejected: does not bound a genuine hang, just delays the failure.
**Consequences.** Easier: resilient builds, no new infra coupling, good practice independent of this incident. Harder: if Vercel also cannot reach the WP host at *runtime*, the live preview shows the empty state until connectivity is fixed host-side (datacenter-IP allowlist) — flagged to the lead.

## 2026-07-01 — Show pipeline: email → WP → Bandsintown via standalone GitHub Action
**Stage:** 03-build
**Type:** Architecture
**Status:** accepted — satisfies the "Future requirement — Email-to-event" note above

**Context.** Meg must add each show twice — WordPress (site source of truth) and Bandsintown, which offers no public write API (dashboard, ticketing-partner auto-detect, or CSV Event Upload only). ## 2026-07-01 — /shows past-shows pagination: backward-walk + same-origin proxy

## 2026-07-08 — Hero backdrop first-paint nudge keyed to `img.decode()`, not the `load` event
**Stage:** 03-build
**Type:** Architecture
**Status:** accepted — amends the nudge mechanism inside the 2026-07-04 "Homepage scroll architecture" scene; the temporary-nudge design (no permanent `will-change`/transform at rest) stands unchanged

**Context.** The 2026-07-04 scene's known compromise — a one-frame transform nudge on the fixed `.backdrop` when the hero photo's `load` event fires, forcing Chrome to re-rasterize a fixed layer whose image decodes after first paint — was still not fully reliable per the client report: on some cold loads the photo only snapped to full-bleed on the first scroll. Root cause: the `<img>` carries `decoding="async"`, which splits the decode step from the `load` event — `load` fires when the bytes arrive, but the bitmap may not be decoded yet, so the nudge could run before there were pixels to rasterize and the repaint it forced painted nothing. The permanent `will-change` alternative was already tried and reverted (renders the photo a beat late at first paint — documented in HomeScene.module.css).
**Decision.** Key the nudge to `img.decode()` — the imperative Decoding API promise, which resolves only once the image is actually paintable and waits for load internally (covers the cached/`complete` case) — with a fallback to the `load` event if `decode()` rejects; and force a synchronous reflow (`offsetHeight` read) immediately before the transform toggle so it lands on fresh layout instead of racing the browser's own pending invalidation. `decoding="async"` + `fetchPriority="high"` on the LCP image are unchanged.
**Rationale.** `decode()` is strictly later-or-equal to `load`, so the readiness signal can only tighten the race — it is the signal that actually means "rasterizable now." Keeping `decoding="async"` preserves the non-blocking decode for LCP; switching to `decoding="sync"` would move the decode cost onto the first presentation frame for no gain once the nudge waits on `decode()`.
**Alternatives considered.** (1) `decoding="sync"` — rejected: blocks the presentation frame on the decode; `decode()` gets the same guarantee without the cost. (2) Permanent `will-change`/transform at rest — rejected: the already-reverted regression (photo late at first paint). (3) Keep the `load`-keyed nudge and add retries — rejected: retries paper over the wrong signal instead of using the right one.
**Consequences.** Easier: the nudge now fires when it can actually work; no change to the scene, release, or reduced-motion paths (verified: entrance, pin, release at the marker, and scroll-back reset all behave identically in preview). Harder: the underlying race is a cold-cache Chrome behavior that cannot be forced locally (dev serves the image instantly), so final confirmation is repeated cold-cache loads against a deployed preview — flagged for the next preview review.

## 2026-07-09 — Boot veil: procedural moving stage-lights replace the photo
**Stage:** 03-build
**Type:** UX / design tradeoff · Architecture
**Status:** accepted — amends the 2026-07-08 "Home boot veil" entry (lifecycle, timing, exit hand-off, session cache, a11y, inert, CLS all stand unchanged); supersedes only the veil's VISUAL layer (photo → procedural lights)

Reduced motion freezes every light at its authored REST frame — a fully composed, lit stage, never blank.
**Design process.** The three candidate rendering techniques (pure-CSS gradient cones / SVG cone+blur / layered radial-sweep) were generated as independent designs and scored by a judge panel (blend-mode-safety + perf weighted highest, then perceptible-motion, then craft); pure-CSS cones won (SVG's `feGaussianBlur`-under-rotation is an iOS-Safari perf gamble; the radial-sweep's 130vw conic layers cost first-composite raster). The winner absorbed the runners-up's best ideas (the sweep layers, rebuilt cheap; the lamp blooms) per the panel's build spec; `will-change` was capped to beams + sweeps only (10 promoted layers) per the panel's perf red-flag.
**Alternatives considered.** (1) Keep the photo, drop only `mix-blend-mode` — rejected: fixes the flash but not the dead beams (still baked-in); the client wanted movement. (2) Re-key the photo drift to a bigger amplitude — rejected: still can't move individual beams, and a large whole-image pan reads as a wobble, not lighting. (3) Canvas/WebGL volumetric beams — rejected: heavy per-frame main-thread work over the LCP while a live fetch runs; CSS transforms are free on the compositor. (4) SVG cones with blur — rejected by the panel (filter-under-rotation perf risk on iOS).
**Consequences.** Easier: the lights genuinely move, nothing blend-flashes, the veil ships no image on the critical path (faster, LCP = logo), and the whole scene is retunable via tokens + per-fixture literals. Harder: a ~26-layer CSS scene is more markup than two `<img>`; per-fixture geometry is Figma-art-directed-by-eye (not a 1:1 export, since the photo is gone — the Figma frames 148:292/295 remain the art-direction reference); the composited-alpha look is "lights over a dark stage," not true additive screen blending (the safe trade for killing the flash). Verified: `tsc` + `next build` clean; beams measured rotating (b3 −9°→−5°, b7 22°→27° over 5s) with all blend-modes `normal`/filter `none`; 390/1440 + reduced-motion + full exit (hold→swell bloom→fade→hero entrance) all correct against a blackhole-WP dev instance (real serverEmpty SSR). Cross-browser (Firefox/iOS Safari) profiling is the remaining Gate-3 item.

## 2026-07-11 — Live backfill run: metric set frozen, two real fixes found
**Stage:** 03-build
**Type:** Architecture
**Status:** accepted — closes the PLAN.md §0/§10 "verify live metric names before freezing" flag

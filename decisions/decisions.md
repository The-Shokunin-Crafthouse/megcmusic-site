# Decisions Log

Append-only log of non-trivial decisions made on this project. Entries are not edited in place — if a decision is reversed, a new entry records the reversal and references the original.

## What belongs here

- Decisions with irreversible or cross-cutting consequences
- Trade-offs that took meaningful discussion
- Scope changes, gate bypasses, and deferred items
- Stage closures (Gate 1, Gate 2, Gate 3, Gate 4, Close)
- Retrospective entries at day 14 post-launch

## What does not belong here

- Transient implementation notes → stage `build-notes.md`
- Bugs → `stages/04-review/output/punch-list.md`
- Design exploration → `stages/02-design/claude-design/` or `./figma/`

## Entry format

```
## YYYY-MM-DD — [short title]
**Stage:** [01-brief | 02-design | 03-build | 04-review | 05-launch]
**Type:** [Stack / tech choice | UX / design tradeoff | Architecture | Product / scope call]
**Status:** [proposed | accepted | superseded by <date-title> | reversed]

**Context.** What situation forced the decision. Include relevant constraints — timeline, prior decisions, what would happen if no choice were made.
**Decision.** What was chosen. One sentence, starting with a verb.
**Rationale.** Why — the reasoning behind the choice.
**Alternatives considered.** What else was on the table and why it was ruled out. At least one alternative; if only one option existed, say so.
**Consequences.** Easier: what this simplifies or de-risks. Harder: what this constrains or makes more expensive to change.
```

## 2026-07-10 — Meta Graph API access: System User token over Instagram Login
**Stage:** 03-build
**Type:** Architecture
**Status:** accepted

**Context.** The existing Social Playbook tab (`megs-playbook`) showed static best-practice text with no real account stats — Instagram/Facebook block unauthenticated scraping, so live post-performance data requires an authenticated Graph API path. Meghan's Instagram (`@meghanclarissecave`) is linked to her "Meghan Clarisse Music" Facebook Page inside her Meta Business Portfolio ("Meghan"). Two credential paths were available: a Meta Business System User token, or an Instagram-Login (Instagram API with Instagram Login) user token tied to a logged-in Instagram account.
**Decision.** Use a Meta Business System User (`megcmusic-automation`, Full access to both the Page and the Instagram account) with a long-lived System User access token, stored as `META_SYSTEM_USER_TOKEN` in Vercel (Production + Preview).
**Rationale.** A System User token is designed for exactly this shape of integration — unattended, server-side, no human session to expire or re-authenticate. It's scoped to the business portfolio rather than a personal login, doesn't depend on Meghan's own Instagram session staying valid, and survives password/device changes on her end. The Instagram-Login path would have tied the integration to a personal account session with a shorter natural lifespan and no clean way to scope permissions to just the automation's needs.
**Alternatives considered.** Instagram API with Instagram Login (user-token path) — rejected: ties the credential to a personal login session rather than a business-scoped service identity, more fragile for an unattended Vercel cron job.
**Consequences.** Easier: token is decoupled from any individual's login state, permissions are explicitly scoped (`instagram_basic`, `instagram_manage_insights`, `pages_read_engagement`, `pages_show_list`), regeneration doesn't require Meghan's involvement. Harder: requires maintaining a Meta Developer app (`Business`, App ID `1020080587391692`) and system user in Business Settings as ongoing infrastructure; a second, orphaned "Business" app (App ID `3187283798124578`, Business: None) was created by accident mid-setup and should be deleted once the real one is confirmed stable, to avoid future mix-ups. Verified end-to-end 2026-07-10: `me/accounts` resolved Page ID `108048260606098` → Instagram Business Account ID `17841401582839394`, and a live `insights?metric=reach&period=day` call returned real data. The token used during that verification was pasted in a chat transcript (via Graph API paging URLs) and was rotated immediately after — the token now live in Vercel is a fresh regeneration, not the one exposed during testing.

## 2026-06-16 — Web fonts via Google Fonts @import
**Stage:** 01-brief
**Type:** Stack / tech choice
**Status:** accepted

**Context.** The brand type system — Lora, Open Sans, Praise, Newsreader — must load on every surface from scaffold onward. Studio learnings prefer self-hosting display faces (`self-host-variable-font-axes`, `font-display-optional`) to avoid the visible late-swap re-render.

**Consequences.** Easier: type system correct immediately; no font files to manage now. Harder: a render-blocking CDN `@import` and possible swap flash remain until the Gate 3 self-host pass; must be revisited before launch.

## 2026-06-16 — Bound Events API calls so a slow upstream can't fail the ISR build
**Stage:** 03-build
**Type:** Architecture
**Status:** accepted

**Context.** The first Vercel preview build prerendered `/` (now fetching events) and timed out — "took more than 60 seconds", three attempts, then failed. The API answers in <1s from a normal network and at every page size, so query cost is not the issue; the Vercel build region intermittently cannot reach `megcmusic.com` and the fetch hangs to the 60s static-generation wall. **Alternatives considered.** (1) `force-dynamic` — rejected: drops ISR (WORKSPACE: ISR only). (2) Reduce `per_page` — rejected: the API is fast at all sizes; size is not the cost. (3) Raise the timeout only — rejected: does not bound a genuine hang, just delays the failure.
**Consequences.** Easier: resilient builds, no new infra coupling, good practice independent of this incident. Harder: if Vercel also cannot reach the WP host at *runtime*, the live preview shows the empty state until connectivity is fixed host-side (datacenter-IP allowlist) — flagged to the lead.

## 2026-07-01 — Show pipeline: email → WP → Bandsintown via standalone GitHub Action
**Stage:** 03-build
**Type:** Architecture
**Status:** accepted — satisfies the "Future requirement — Email-to-event" note above

**Context.** Meg must add each show twice — WordPress (site source of truth) and Bandsintown, which offers no public write API (dashboard, ticketing-partner auto-detect, or CSV Event Upload only). ## 2026-07-01 — /shows past-shows pagination: backward-walk + same-origin proxy

**Status:** accepted

## 2026-07-08 — Hero backdrop first-paint nudge keyed to `img.decode()`, not the `load` event
**Stage:** 03-build
**Type:** Architecture
**Status:** accepted — amends the nudge mechanism inside the 2026-07-04 "Homepage scroll architecture" scene; the temporary-nudge design (no permanent `will-change`/transform at rest) stands unchanged

**Context.** The 2026-07-04 scene's known compromise — a one-frame transform nudge on the fixed `.backdrop` when the hero photo's `load` event fires, forcing Chrome to re-rasterize a fixed layer whose image decodes after first paint — was still not fully reliable per the client report: on some cold loads the photo only snapped to full-bleed on the first scroll. Root cause: the `<img>` carries `decoding="async"`, which splits the decode step from the `load` event — `load` fires when the bytes arrive, but the bitmap may not be decoded yet, so the nudge could run before there were pixels to rasterize and the repaint it forced painted nothing. The permanent `will-change` alternative was already tried and reverted (renders the photo a beat late at first paint — documented in HomeScene.module.css).
**Decision.** Key the nudge to `img.decode()` — the imperative Decoding API promise, which resolves only once the image is actually paintable and waits for load internally (covers the cached/`complete` case) — with a fallback to the `load` event if `decode()` rejects; and force a synchronous reflow (`offsetHeight` read) immediately before the transform toggle so it lands on fresh layout instead of racing the browser's own pending invalidation. `decoding="async"` + `fetchPriority="high"` on the LCP image are unchanged.
**Rationale.** `decode()` is strictly later-or-equal to `load`, so the readiness signal can only tighten the race — it is the signal that actually means "rasterizable now." Keeping `decoding="async"` preserves the non-blocking decode for LCP; switching to `decoding="sync"` would move the decode cost onto the first presentation frame for no gain once the nudge waits on `decode()`.
**Alternatives considered.** (1) `decoding="sync"` — rejected: blocks the presentation frame on the decode; `decode()` gets the same guarantee without the cost. (2) Permanent `will-change`/transform at rest — rejected: the already-reverted regression (photo late at first paint). (3) Keep the `load`-keyed nudge and add retries — rejected: retries paper over the wrong signal instead of using the right one.
**Consequences.** Easier: the nudge now fires when it can actually work; no change to the scene, release, or reduced-motion paths (verified: entrance, pin, release at the marker, and scroll-back reset all behave identically in preview). Harder: the underlying race is a cold-cache Chrome behavior that cannot be forced locally (dev serves the image instantly), so final confirmation is repeated cold-cache loads against a deployed preview — flagged for the next preview review.

**Type:** UX / design tradeoff · Architecture
**Status:** accepted — amends the 2026-07-08 "Home boot veil" entry (lifecycle, timing, exit hand-off, session cache, a11y, inert, CLS all stand unchanged); supersedes only the veil's VISUAL layer (photo → procedural lights)

**Context.** The 2026-07-08 veil rendered a stage-lights photo as two stacked `<img>` — a base at `mix-blend-mode: luminosity` (10%) and a screen-blend copy whose opacity "breathed" — over the plum ground, with a 36s whole-image drift. The client reported two defects on the deployed veil (confirmed in incognito, so not a cache artifact): (1) the background "flips to a different layer mode" — the blended layer intermittently DROPS to unblended on compositing (a WebKit/Blink bug when a `mix-blend-mode` element also animates/promotes), and luminosity↔normal on a photo is a dramatic flip; (2) "the lights do not move" — the beams are baked into the photo, and the 36s -1.5%/1% whole-image nudge is sub-pixel-imperceptible; the "breath" only brightened, nothing travelled. The client explicitly approved recreating the light sources procedurally ("we don't have to keep the image … recreate the light sources another way so you can move them, use the image as a reference").
**Decision.** Replace the photo with a **procedural CSS concert-lighting scene** (`LoadingVeil.module.css`): 8 beam cones fanning from an upper truss (linear-gradient fill + `clip-path` cone + edge-feather `mask` — no filter), 8 lamp blooms capping each fixture, 7 floor gobo pools, 2 wide slow "room-pass" sweeps, and a haze fill — all composed over a radial plum ground (lifted `--mc-veil-bg` centre → site `--mc-bg` edges, the dark surround beams need to read as light). **Zero `mix-blend-mode`, zero `filter`; animates `transform` + `opacity` ONLY** (compositor-driven, off the main thread). Each beam does a real ~10-12° rotate SWEEP (~1°/s — plainly perceptible, verified) plus an opacity breath; every layer is phase-offset (sweeps 15-31s, breaths 7-14s) so the rig never pulses in unison. The exit "bloom" beat moved from the (deleted) screen-blend photo copy to a dedicated `.bloom` wash (0 → `--mc-veil-swell-opacity` on the swell phase). The stage photo (`public/images/loading/stage-lights.jpg`) is deleted — nothing references it, and the critical path no longer ships a 184KB image (LCP is unambiguously the logo SVG; CLS still 0, fixed overlay). Palette lives in token-map.css (`--mc-veil-c-*`, 6 rgb triplets); per-fixture geometry/phase are documented composition literals in the module (Instastar 2026-07-05 / ShowCard precedent, not design tokens). Reduced motion freezes every light at its authored REST frame — a fully composed, lit stage, never blank.
**Design process.** The three candidate rendering techniques (pure-CSS gradient cones / SVG cone+blur / layered radial-sweep) were generated as independent designs and scored by a judge panel (blend-mode-safety + perf weighted highest, then perceptible-motion, then craft); pure-CSS cones won (SVG's `feGaussianBlur`-under-rotation is an iOS-Safari perf gamble; the radial-sweep's 130vw conic layers cost first-composite raster). The winner absorbed the runners-up's best ideas (the sweep layers, rebuilt cheap; the lamp blooms) per the panel's build spec; `will-change` was capped to beams + sweeps only (10 promoted layers) per the panel's perf red-flag.
**Alternatives considered.** (1) Keep the photo, drop only `mix-blend-mode` — rejected: fixes the flash but not the dead beams (still baked-in); the client wanted movement. (2) Re-key the photo drift to a bigger amplitude — rejected: still can't move individual beams, and a large whole-image pan reads as a wobble, not lighting. (3) Canvas/WebGL volumetric beams — rejected: heavy per-frame main-thread work over the LCP while a live fetch runs; CSS transforms are free on the compositor. (4) SVG cones with blur — rejected by the panel (filter-under-rotation perf risk on iOS).
**Consequences.** Easier: the lights genuinely move, nothing blend-flashes, the veil ships no image on the critical path (faster, LCP = logo), and the whole scene is retunable via tokens + per-fixture literals. Harder: a ~26-layer CSS scene is more markup than two `<img>`; per-fixture geometry is Figma-art-directed-by-eye (not a 1:1 export, since the photo is gone — the Figma frames 148:292/295 remain the art-direction reference); the composited-alpha look is "lights over a dark stage," not true additive screen blending (the safe trade for killing the flash). Verified: `tsc` + `next build` clean; beams measured rotating (b3 −9°→−5°, b7 22°→27° over 5s) with all blend-modes `normal`/filter `none`; 390/1440 + reduced-motion + full exit (hold→swell bloom→fade→hero entrance) all correct against a blackhole-WP dev instance (real serverEmpty SSR). Cross-browser (Firefox/iOS Safari) profiling is the remaining Gate-3 item.

## 2026-07-24 — Generation daemon runs as a per-user LaunchAgent, not a system LaunchDaemon: Keychain-stored CLI credentials are unreachable from the system domain

**Stage:** 03-build
**Type:** Architecture · Bug fix
**Status:** accepted — supersedes the 2026-07-13 LaunchDaemon decision and the `agent/README.md` section implementing it

**Context.** First real install of `agent/playbook-agent.mjs`, on Meghan's own Mac under her own account (`meggybahn`) and her own Claude Pro subscription — not the second-account-on-Levi's-Mac arrangement the 2026-07-13 ADR assumed. The `claude` CLI was not installed on the machine at all (nothing on PATH, in Homebrew, or under npm global; the Claude desktop app does not ship the CLI), so it was installed via the native installer to `~/.local/bin/claude` (v2.1.219). `sudo bash agent/install-launchdaemon.sh meggybahn` then succeeded on every check the script makes — plist written `root:wheel` 644, bootstrapped into the `system` domain, `launchctl list` showing the label, log file non-empty — and the daemon still failed every job: it claimed a real queued row and marked it `error` 4.5s later, `claude` having returned the literal string `Not logged in · Please run /login`, which fails `JSON.parse` on both the first attempt and the one-shot repair retry. The cause is that the CLI stores credentials in the macOS **login Keychain** (verified: no `~/.claude/.credentials.json` or any on-disk credential file exists), and a LaunchDaemon runs in the system bootstrap context, which has no access to a user's login keychain — **even while that user is in an active GUI session**. Keychain reachability follows the security session, not merely the unlock state. The 2026-07-13 ADR chose a LaunchDaemon specifically to survive a full log-out; that benefit is unobtainable for any Keychain-authenticated CLI, so the trade it was accepting did not exist. The same finding invalidates the README's claim that a first interactive login "unlocks Keychain access" for a later system-domain daemon.
**Decision.** (1) Install via `agent/install-launchd.sh` — the per-user LaunchAgent in `gui/<uid>` — and treat that as the supported path on this machine. Verified working: the identical job that the LaunchDaemon killed completed in 13.7s once re-queued, and four of the six job kinds have since run green through the installed agent. (2) `agent/install-launchdaemon.sh`, its plist template, and its uninstaller stay in the repo but are documented as **unusable with Keychain-stored CLI credentials**, for the dedicated-account scenario only if that CLI is ever authenticated by a means a system daemon can read (e.g. an env-var API key) — which this project deliberately does not use, since the whole point is running on Meghan's subscription rather than a metered key. (3) Accept the resulting availability model: the agent runs while she is logged in, survives Fast User Switching and screen lock, pauses on sleep, and stops on full log-out or restart — recovering by itself at next login via `RunAtLoad`. Jobs queued while it is down stay `queued` and get claimed on return.
**Alternatives considered.** (1) Keep the LaunchDaemon and pre-unlock the keychain from a boot script — rejected: it would mean storing the keychain password in a root-readable file, trading a working setup for a credential leak. (2) Move the CLI to an `ANTHROPIC_API_KEY` in `agent/.env`, which a system daemon *can* read — rejected: that is a metered API key, the exact cost model PLAN.md §2/§5 exists to avoid. (3) Leave the LaunchDaemon installed and disabled-by-flag as a fallback — rejected: it would silently and destructively fail any job it did claim; a stopped agent leaves work `queued`, a broken one marks it `error`. (4) A `launchd` `LimitLoadToSessionType: Aqua` daemon — not taken: that is a LaunchAgent by another name, and the existing script already does it correctly.
**Consequences.** Easier: no `sudo` in the install path at all; the failure mode is now "nothing happens, jobs wait" rather than "jobs die with a confusing parse error"; and the agent's liveness is tied to the session that owns the credentials, so the two cannot drift apart. Harder: the daemon genuinely does not run when nobody is logged in, so the machine has to be left logged in (Fast User Switching is fine — do not log out), and a restart needs a manual login before generation resumes. Worth knowing for diagnosis: a locked or unavailable keychain reproduces *exactly* the LaunchDaemon signature — jobs failing within seconds with `Not logged in` in `agent/logs/agent.log` — so that string, not the job status, is the thing to look for.

## 2026-07-24 — Generation daemon distinguishes a failed queue read from an empty queue; startup preflight on the Supabase credential

**Stage:** 03-build
**Type:** Architecture · Bug fix

**Status:** accepted

**Context.** With an invalid `SUPABASE_SERVICE_ROLE_KEY`, `agent/playbook-agent.mjs` logged `error claiming next job: select queued jobs: Invalid API key` and then `no queued jobs — --once exiting 0`. The claim error was caught to stdout and the loop fell through to the same `if (!job)` branch an empty queue takes, so a credential failure was reported as idleness and exited 0. That defeats `agent/README.md`'s own verification procedure: a misconfigured daemon under launchd satisfies both documented runtime checks — `launchctl list` shows the label and `agent/logs/agent.log` is non-empty — while being structurally unable to ever claim a job. It is precisely the false positive studio learning #45 names (a source artifact's presence is not proof of delivery), reintroduced inside the tool written to avoid it. The claim `UPDATE` swallowed errors the same way, its `if (claimError) return null` treating any failure as a lost race.
**Decision.** Make "query failed" and "query succeeded, zero rows" structurally different outcomes: `claimNextJob` returns `null` only for a genuinely empty queue or a lost claim race (PostgREST `PGRST116` on the `.single()` guard) and throws on everything else; the poll loop routes a claim failure to a new `logError` (stderr → `agent-error.log`, fixed `ERROR` token) instead of stdout, exits 1 under `--once`, and in loop mode keeps retrying with the poll interval doubling to a 60s ceiling and resetting on the first success; and a new `preflightSupabase` reads `generation_jobs` once at startup, exiting 1 on a credential Supabase rejects (401/403, `42501`, `Invalid API key`) and warning-then-continuing on anything else.
**Rationale.** A daemon whose only failure signal is "nothing to do" is worse than one that crashes — the operator has no way to tell working from broken, and the README's checks actively certify the broken state. The split follows the failure's own recoverability: a rejected key cannot be retried into working and needs an `agent/.env` edit, so it should die loudly and let launchd's 10s `ThrottleInterval` crash-loop advertise it; a network blip or Supabase outage does recover on its own, so the loop must survive it without a manual restart. Preflighting at startup moves credential failure from "discovered on the first poll, indistinguishable from idle" to "discovered before the loop begins, with a message naming the fix."
**Alternatives considered.** (1) Exit 1 on any preflight failure, transient or not — rejected: a Supabase blip at boot would crash-loop the daemon rather than let it poll through the outage, and the reported bug is about *visibility*, not about dying more often. (2) Keep the loop crashing out of `main()` on a claim error and rely on launchd `KeepAlive` to restart it — rejected: it discards the in-process state, turns every transient outage into a restart, and gives a `--once` operator a stack trace where an exit code and one line would do. (3) Fix only the swallow in the `--once` path and leave the daemon loop as-is — rejected: the daemon is the surface the README's verification actually covers, so leaving it silent leaves the false positive standing. (4) Log claim failures at normal severity to stdout and let the operator read the log — rejected: `agent.log` is also where routine polling lives; the whole point is a signal that survives a `grep` and a non-zero exit.
**Consequences.** Easier: `grep ERROR agent/logs/agent-error.log` is now a complete answer to "is this daemon actually able to work"; `no queued jobs` means exactly one thing; a wrong key is caught at startup with a message naming the file to edit. Harder: `--once` now has meaningful exit codes, so any script wrapping it must stop treating exit 0 as "ran fine" without checking (the README documents the codes); and the daemon crash-loops under launchd on a bad credential rather than sitting quietly — intended, but it will fill `agent-error.log` until the key is fixed. Verified against a local PostgREST stub across empty-queue, hard-error, `PGRST116` claim-race, failed-claim, and failure-then-recovery scenarios, plus a live `Invalid API key` reproduction; **not** verified end-to-end against a real queued row, because `agent/.env` on this machine still holds the `PASTE_SERVICE_...` placeholder.
## 2026-07-24 — A daemon code change is not live until the LaunchAgent is restarted; verify by process start time, not by file contents

**Stage:** 03-build
**Type:** Process · Bug fix

**Status:** accepted

**Context.** PR #59 relaxed `frameSchema.onScreenText` to allow `""` in both `src/lib/playbook/generation.ts` and `agent/contracts.mjs` (committed 22:03, merged 22:06 local). The LaunchAgent running at that moment had started at **21:59:07** — four minutes earlier. Node resolves an ESM module graph once at process start, so the live daemon still held the old `z.string().min(1)` in memory and would have gone on rejecting exactly the output the merged prompt asks Claude to produce. Every check in `agent/README.md`'s verification section passed the whole time: `launchctl list` showed the label, the log was non-empty, and jobs were completing — because the jobs that happened to run had text on every frame. (2) `KeepAlive`-driven periodic restart — rejected: restarts during a live generation lose the job, and the daemon has no resume. (3) Rely on the plist's `RunAtLoad` and assume login-time restarts are frequent enough — rejected: this machine is rarely rebooted, which is exactly how a four-minute gap became a live one. (4) Version-stamp `contracts.mjs` and have the daemon log its hash at startup — not taken now, but it is the cheap upgrade if this recurs; the start-time comparison needs no code change.
**Consequences.** Easier: a stale daemon is a one-command check rather than an invisible state, and the `agent/README.md` verification section now says so. Harder: the restart is manual and easy to forget, and nothing enforces it — the failure mode it prevents is silent, so the check has to be run deliberately after every `agent/` merge.

The historical log lines that looked like proof say the same thing once read with timestamps: job `42922222` logged `streaming` at 04:00:28.332 and `done` at 04:00:28.718 — 386ms apart, at the end of a 54-second job. Re-running the identical prompt **with** `--include-partial-messages` produces `stream_event` / `content_block_delta` events from 1.57s onward, continuously.
**Decision.** Record that the streaming path is decorative as built and **do not change it in this pass**. The fix is two edits — add `--include-partial-messages` to the spawn args, and handle `event.type === "stream_event"` (`content_block_delta`) alongside the existing `assistant` branch in the stdout parser — but it changes what the PWA sees mid-generation, which is a product-surface call for Meghan, not a decide-and-log one.
**Rationale.** The feature is not broken in a way that costs anything today: the final write is what the job's correctness depends on, and that has always worked. What was broken is the *belief* that progressive output was being delivered and verified — the README asserted it, and a `streaming` line in the log looked like corroboration, so the claim survived review twice. Correcting the record is the part that had to happen now.
**Alternatives considered.** (1) Ship the flag + parser change immediately as an in-standard bug fix — not taken: it is a visible behaviour change to a live app on a stage-gated project, and the ask for this pass was to observe. (2) Delete the streaming path as dead weight — rejected: the `streaming` status is in the migration's `check` constraint and the PWA reads it; removal is a wider change than the fix. (3) Lower `STREAM_SYNC_INTERVAL_MS` — rejected: it addresses timing, and timing was never the problem.
**Consequences.** Easier: `agent/README.md` no longer claims a capability the daemon does not have, and the fix is written down at the exact two call sites. Harder: until it is taken, a long generation shows the PWA nothing between `running` and `done`, so the perceived-latency work the streaming path was meant to support is not actually in place — and a future reader could re-derive the same false confidence from the `streaming` status existing in the schema.

## 2026-07-24 — An exhausted Claude allowance is misclassified as a contract-validation failure and killed by the repair retry; retry semantics unchanged pending owner decision

**Stage:** 03-build
**Type:** Architecture · Risk

**Status:** accepted (observation; semantics unchanged by instruction)

**Context.** Observed live, not hypothesised. After nine `claude -p` spawns in ~8.5 minutes (six jobs, two of which spent a second spawn on a repair retry, including two `storyboard` runs at `--effort high`), the CLI began returning prose starting `You've hit…` where JSON was expected. The daemon's `validateOutput` did what it does with any non-JSON reply: reported `JSON.parse failed`, spawned the **repair retry 2.8 seconds later** — which hit the same limit — and marked the job `error` with `Validation failed after repair retry: JSON.parse failed: Unexpected token 'Y', "You've hit"…`. The queued duplicate behind it then died the same way in 6.1 seconds, spending two more spawns against an already-refusing endpoint. The limit was **transient**: a plain `claude -p` probe succeeded later in the same session with no code or config change, and a full storyboard generation completed normally at 05:26 UTC. Per-kind cost for sizing: `tip_review` ~10s, `titles` ~16–18s, `questions` ~7–20s, `tip_derivation` ~20s, `storyboard` ~42–55s at `high` (~99s when a repair round trip is involved); one spawn per job, two when validation fails.
**Decision.** Do not change retry or backoff semantics in this pass — instructed, and correct anyway without an owner decision on the trade-off. Record the misclassification and the three candidate mitigations so the decision can be made on evidence: (a) detect an auth/quota refusal *before* validating, by matching the raw reply against the CLI's refusal strings, and mark the job `error` with a message naming the real cause instead of a JSON parse error; (b) do not spend the repair retry when the first failure was a refusal rather than malformed JSON — the repair prompt cannot fix a quota; (c) treat a refusal as retryable at the *queue* level (leave the row `queued`, back off) rather than terminal, since the limit demonstrably recovers on its own.
**Rationale.** The damage is not that the job failed — it is that a recoverable, self-healing upstream condition is recorded as a permanent contract failure, in a message that points at the prompt and the schema. Anyone debugging `Validation failed after repair retry: JSON.parse failed` will go read `agent/prompts/storyboard.md` and `contracts.mjs`, both of which are correct. Meanwhile the daemon's response to being rate-limited is to immediately issue another request, and then to pull the next queued job and issue two more.
**Alternatives considered.** (1) Ship (a) alone as a pure diagnostics improvement — genuinely tempting and nearly risk-free, but it still edits the failure path of a live daemon, so it waits for the same decision. (2) Widen the spawn-failure retry (2 attempts, 5s/15s) to cover refusals — rejected as written: 20 seconds is far short of a limit window, so it would burn three spawns instead of two and still fail. (3) Reduce load by dropping `storyboard` back to `medium` — rejected: the 2026-07-24 effort ADR measured `high` as both cheaper and faster once repair round trips are counted. (4) Detect the limit and pause the whole poll loop until a reset time — the most correct answer if the CLI exposes a reset timestamp; unverified whether it does, so not proposed as the first step.
**Consequences.** Easier: the failure signature is now documented, so the next `You've hit` error is recognisable as a quota event in seconds rather than a prompt-drift investigation. Harder: as it stands, a rate limit during a real session produces dead jobs Meghan has to re-run by hand, and each dead job costs two spawns against the very allowance that is exhausted — so the daemon makes a limit event slightly worse rather than riding it out. This is the single largest remaining reliability gap in the daemon.

## 2026-07-26 — Take all three deferred daemon fixes: titles frames, refusal classification, real partial streaming

**Stage:** 03-build
**Type:** Architecture · Bug fix

**Status:** accepted — supersedes the "fix deferred" and "semantics unchanged" positions in the three 2026-07-24 ADRs above, on Meghan's instruction.

**Context.** The 2026-07-24 verification pass identified three defects and deliberately shipped none of them: the `titles` job never receiving the storyboard frames, an exhausted Claude allowance being recorded as a contract-validation failure, and partial-output streaming not working at all. Two were held for a product call and one for an explicit instruction not to change retry semantics without an ADR. This is that ADR; Meghan asked for all three.

**Decision.**

*(1) `titles` frames.* Add `frames: z.array(z.unknown()).optional()` to `jobInputSchemas.titles` and send it from `handleFreshTitles`. `unknown` rather than `frameSchema` because the daemon only serialises these into a prompt — a stricter shape would reject a storyboard the renderer is happy with, for no gain. `context` stays in the schema: the daemon still accepts it and callers outside the page may use it, with `frames` winning when both are present.

*(2) Refusal classification.* Classify the raw reply **before** validating it. `detectCliRefusal` splits refusals by whether waiting fixes them: quota/rate ("you've hit … limit", "too many requests") are transient; auth/billing ("not logged in", "invalid api key", "credit balance is too low") are permanent. Permanent refusals error the job immediately with the real reason and an `ERROR` line naming the fix. Transient refusals put the row back to `queued` and pause claiming for 5/15/30 minutes, up to three requeues, then error with a message that still names the cause. The one-shot repair retry is skipped entirely for both — it exists for malformed JSON and cannot fix a quota. The detector is deliberately conservative: anything parsing as JSON, opening like JSON, or longer than 600 characters is never a refusal, because a false positive would requeue or kill a job whose reply was merely malformed.

*(3) Streaming.* Add `--include-partial-messages` and handle `stream_event`/`content_block_delta` beside the existing `assistant` branch. Because both arrive for the same content with the flag on, the accumulator is split in two — `deltaText` (progressive, drives the ~2s sync) and `assistantText` (authoritative, drives the result) — rather than appending both to one buffer, which would double every reply.

**Rationale.** These were separated by risk, not by size, and the risk ordering held up: (1) and (3) are additive, while (2) changes what happens to a job on a failure path, which is why it needed the instruction. Taking (2) as *classification plus queue-level backoff* rather than as more retries matters — the observed failure was not "too few attempts", it was attempts aimed at a condition no retry could fix, issued into the very limit that had just refused. Pausing the claim loop is the part that stops one limit event from consuming the whole queue; the 2026-07-24 trace shows a second job dying 6.1 seconds after the first for exactly that reason.

**Alternatives considered.** (1) Send `context: JSON.stringify(frames)` from the call site instead of a typed `frames` array — rejected: it routes real structured data through a free-form string and lands on the daemon's fallback branch rather than its primary one. (2) Add an `attempts` column to `generation_jobs` for the requeue bound — rejected for now: it needs a migration for a counter that only matters during an active outage, and an in-memory `Map` keyed by job id gives the same bound in loop mode. Known limitation, accepted: under `--once` each invocation is a fresh process, so the count always restarts at 0 and the bound never accumulates — irrelevant to the deployed LaunchAgent, which runs the loop. (3) Pause the entire daemon (exit and let launchd restart) on a limit — rejected: it discards in-process state and turns a 5-minute wait into a crash-loop. (4) Parse a reset timestamp out of the refusal and sleep exactly that long — not taken: the message format is undocumented and would silently rot; fixed escalating cooldowns degrade predictably. (5) Ship (2) as diagnostics only, without the requeue — rejected once the instruction arrived: it would leave the job dead, which is the actual harm.

**Consequences.** Easier: a rate-limited job survives to run later instead of needing a manual re-queue; the stored `error` on a refusal now names the real cause rather than pointing at a prompt that is correct; "Fresh titles" reasons about the actual storyboard; and a long generation reports genuine progress (measured: 7 partial writes across a 102.5s storyboard, versus zero before). Harder: three new tunables (`RATE_LIMIT_COOLDOWNS_MS`, `MAX_RATE_LIMIT_REQUEUES`, `REFUSAL_MAX_LENGTH`) and a refusal-pattern list that will drift as the CLI's wording changes — a reworded limit message degrades to the old behaviour (dead job, misleading error) rather than to something worse, but it does degrade silently. The patterns are the thing to check first if a `JSON.parse failed` error quoting English prose ever reappears.

**Verification.** All three at the destination, not at `done`. Streaming: partial output landing at ~2s intervals while `status='streaming'` on a 102.5s storyboard (148 → 5152 chars over 7 writes) and on a 16s `questions` job. Titles: the job created by the real "Fresh titles" button carries `frames` with 6 entries matching the rendered storyboard, and the returned rationales cite "frame 5" and "the cold-open frame". Refusals: driven end to end against stub CLIs emitting the exact observed strings — transient requeued the row to `queued` with a `WARN` and **1** spawn (no repair retry), permanent errored immediately with `claude CLI unavailable: Not logged in · Please run /login` and **1** spawn, and a malformed-JSON control still took **2** spawns, confirming the repair path is intact. 14 classifier cases pass, including the negative cases that must reach the repair retry.

## 2026-07-28 — Safe-area insets offset the chrome, never the pick artwork; nav offsets use `max()`, not a sum

**Stage:** 03-build
**Type:** UX / design tradeoff · Bug fix
**Status:** accepted — amends the 2026-07-22 corner-pick ADR's `.corner` placement and the BottomNav offsets it set

(3) Leave the pill at the sum and treat 50px as correct for installed devices — rejected: it is not a considered value, it is two offsets that happened to add.
**Consequences.** Easier: the corner mark is launch-mode-independent, and one `max()` covers notched, non-notched and browser-tab cases without a media query or a display-mode branch. Harder: `env(safe-area-inset-bottom)` is now read in three places with the same `max()` idiom, and a fourth consumer has to remember the idiom rather than reaching for `calc(x + env(...))`. Verified by measurement against a simulated 34px inset — pick layer flush at 0px and the wedge's visible height unchanged (90 of 215.8px) in both modes, pill 16px in a tab / 34px installed. **Not** verified on the physical device: `display-mode: standalone` is not emulable in headless Chromium, so the inset was simulated by mirroring each rule. ## 2026-07-28 — `/run-state`'s two unbounded selects paged; `.in()` id lists chunked

**Stage:** 03-build (bug fix)
**Type:** Correctness · Data access

**Status:** accepted

**Context.** `GET /api/outreach/run-state` is the weekly automation's entire read surface, and both of its list queries were unbounded `.select()`s. PostgREST caps an unbounded select at its `max-rows` setting — 1000 by default — and reports the truncation nowhere: no error, no flag, no count (studio learning #84). The first query, `prospects` filtered to the actionable statuses, *is* the work list, so past row 1000 a prospect is not merely missed in a display — it is never contacted and never followed up, indefinitely, because every subsequent run reads the same truncated head. The second, every inbound message for every actionable prospect, spans a row per message rather than per prospect, so it crosses 1000 well before the pipeline does; truncating it undercounts `inbound_this_cycle`, and an undercount of zero is exactly the condition that sends a follow-up to someone who already replied. Neither failure produces an error to notice.

**Decision.** Add `fetchAllPages` and `chunkIds` to `src/lib/api/appDb.ts` and route both queries through them. `fetchAllPages(page)` calls a caller-supplied builder with `.range(from, to)` until a page returns empty, returning `{ rows, error }` — error *returned*, not thrown, matching the supabase-js convention these handlers already branch on (learning #85). Each paged query carries `.order("id", { ascending: true })`; both tables have a uuid primary key, and without a stable sort the page boundary is nondeterministic and rows can repeat or vanish across it. The message query's id list is additionally chunked at 200 ids per `.in()`.

**Rationale.** Paging advances by the number of rows actually returned rather than by the page size, so a server-side `max-rows` set *below* our 1000 would page correctly instead of stopping one short page in and reintroducing the same silent truncation one layer down; the cost is one extra empty request per call, which is the right trade on a route whose whole failure mode is silent incompleteness. The chunking was a judgement call rather than a required part of the fix: PostgREST takes filters in the query string, so a single `.in()` over every actionable prospect grows the URL without bound — at ~39 bytes per quoted uuid, a few hundred ids already approach the common 8KB request-line limit, and the resulting 414 would land on the automation, not a human, right at the scale where the paging fix starts to matter. Pre-empting it costs a loop. Chunks run sequentially: correctness over latency on a weekly job.

The `templates` query in the same handler is deliberately left unbounded — it is bounded by schema (one initial per category plus three global follow-ups, ~9 rows), and paging it would imply a cap that cannot be reached.

**Alternatives considered.** (1) A bare `.range(0, 9999)` on each query — rejected: it moves the silent cap rather than removing it, and picks a magic number nothing enforces. (2) `.limit()` plus a count check that errors when the total exceeds the page — rejected: fails the run rather than completing it, on a route with no human watching. (3) Push the cycle comparison into the query (a join or an RPC) so the message read returns counts rather than rows — genuinely better, and it would sidestep both the row volume and the id list, but it means a DB function and a migration for a route that is otherwise correct; deferred, not dismissed. (4) Chunk-parallel with `Promise.all` — rejected as premature on a weekly job, and it removes the natural backpressure on the service-role client.

**Consequences.** Easier: the automation's work list is now complete by construction, and the two helpers are the obvious landing place for the same fix elsewhere. Harder: a large pipeline now costs multiple round trips per run rather than one, and any future paged query in this codebase must remember the stable `.order()` — the helper's doc comment says so, but nothing enforces it. **Standing gap, not fixed here:** `GET /api/outreach/summary` carries the identical defect on its own `prospects`, `templates` and `messages` selects, and `POST /api/outreach/prospects` reads `select("email, org")` unbounded for its duplicate check — a truncated read there admits duplicates rather than merely hiding rows. Those were left untouched deliberately: this session was told the summary route had just been fixed and found it had not, which is the signature of a parallel session working the same file (studio learning #75), and a competing edit to a shared route is worse than a second PR.

**Verification.** `npx tsc --noEmit` clean. Logic traced by hand: `chunkIds([])` returns `[]`, so the message loop is skipped for an empty pipeline exactly as the old `prospects.length > 0` guard did; `fetchAllPages` terminates on the first empty page and cannot loop without advancing, since it returns as soon as a batch is empty and otherwise advances by that batch's length. Not exercised against a >1000-row table — the live pipeline is far below the cap, which is precisely why the defect was invisible.

## 2026-08-29 — Phase 1 implementation decisions: transient debounce (not wp-cron), PAT scope correction, custom page-slug location rule, plugin lint CI

**Stage:** 03-build (sprint-11-wp-editability, Phase 1)
**Type:** Architecture
**Status:** accepted

**Decisions.**
1. **The 60s dispatch debounce is a transient, not a wp-cron event.** This install's cron option intermittently fails to persist (Bluehost error logs, 2026-08-27 entry) — a `wp_schedule_single_event` debounce would silently drop pings. Leading-edge transient instead: first save dispatches immediately; saves inside the window are suppressed; bursts collapse in the receiving workflow's GHA concurrency group (one running + one queued run, the queued run builds final state); the Phase-4 nightly rebuild self-heals stragglers.

The contract's *mechanism* (repository_dispatch, event `wp-content-updated`) is kept as written; only the stated scope was unachievable. Mitigation for the wider scope: fine-grained token limited to this single repo, stored only as a `wp-config.php` constant (never plugin file, never DB), 1-year expiry.
3. **Custom ACF location rule `megc_page_slug`** so the Poetry field group can target the `site-poetry` page by slug before the page exists (it is created in Phase 2); all other groups pin existing page IDs.
4. **`wp-plugin-lint.yml` CI**: PHP 8.3 `php -l` over the plugin + JSON validity on every PR touching `wp-plugin/**` — the 2026-08-27 outage class (PHP-incompatible plugin code fataling on admin hooks) gets a deterministic gate. No local PHP exists on the dev Mac, so CI is the lint surface.

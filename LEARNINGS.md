## 2026-06-17 — Turbopack silently strips external CSS `@import url()`
**Context:** Google Fonts were loaded via `@import url('https://fonts.googleapis.com/...')` in `globals.css`. After the Sprint-2 build landed on Vercel the entire type system rendered in system fallbacks — `document.fonts` was empty, zero requests reached googleapis. Investigation confirmed Next.js 16's Turbopack strips external `@import url()` from CSS during the build step; local `@import` (e.g., `token-map.css`) inlines fine.
**Lesson:** Never load a third-party stylesheet via CSS `@import url()` in a Next.js project running Turbopack. Use `<link rel="stylesheet">` + `<link rel="preconnect">` in `app/layout.tsx` `<head>` for third-party CSS (Google Fonts, icon libraries, etc.), or `next/font/*` for font files. The `<link>` reaches the browser verbatim regardless of bundler behavior.
**Trigger:** Any Next.js project on Turbopack (Next 15+/16+) that loads a third-party stylesheet. Also: if fonts look wrong after a Vercel build, check `document.fonts` in-browser before debugging CSS — if it is empty, the import was stripped.

## 2026-06-16 — Bound ISR server fetches with `AbortSignal.timeout` to prevent build hangs
**Context:** First Vercel preview build of the Shows section timed out at the 60s static-generation wall — three attempts, all failed. The Tribe Events API answers in < 1s from a local network; the issue was that the Vercel build region intermittently could not reach `megcmusic.com`, causing the fetch to hang indefinitely rather than reject.
**Lesson:** Every external API call inside a Next.js ISR page must carry `signal: AbortSignal.timeout(N)` (8–12s is a reasonable ceiling). The page's existing `try/catch` then renders the empty state instead of stalling the build. Pair with `staticPageGenerationTimeout: 120` in `next.config.ts` for ISR pages that legitimately run longer. A slow upstream must never be able to stall a deploy.
**Trigger:** Any Next.js ISR page that calls an external or third-party REST endpoint at build time. Apply this pattern at the point the fetch client is written — do not wait to discover the gap in production.

## 2026-06-16 — Tokenize off-grid Figma values rather than snapping when the client has signed off the spec
**Context:** Figma card padding was 19px — 3px off the 8pt grid. The initial build snapped it to 16px (`--mc-space-3`), per studio discipline. Client review flagged the visible gap; the directive was fidelity to the Figma file.
**Lesson:** When a Figma value is off-grid but the client has explicitly approved the design (i.e., Figma IS the signed spec), tokenize the exact value (`--mc-card-pad-y: 19px`) and note the off-grid choice in the token comment. The token enforces consistency across all card instances; a snap creates a silent spec conflict. Grid discipline defers to a client-approved spec.
**Trigger:** Any Figma-to-code fidelity pass where exact Figma values conflict with the 8pt grid. If the client hasn't reviewed yet, snap and flag for review; if the Figma is signed off, tokenize exactly.

## 2026-06-16 — Add a `-ink` token variant when a brand fill color fails AA as text
**Context:** Brand red `#d13e5b` (fill color) measured 3.9:1 on the cream card surface `#f7eadd` — below the 4.5:1 AA floor for 16px regular text. The venue name is a link, making legibility doubly important.
**Lesson:** A fill hue and its text-use hue are separate concerns. When a color used as a fill fails AA at text size, add a paired `-ink` token (`--mc-accent-red-ink: #bb314f`) tuned just dark enough to pass. Keep the base token for fills, borders, and decorations; point all text uses at `-ink`. Never modify the base token to fix a text case — it silently shifts every downstream fill use.
**Trigger:** Any time a brand or accent color is used for both fill and text elements. Spot-check text contrast independently from fill contrast at the token-additions stage.

## 2026-07-05 — Top-anchored route UI must reserve clearance for the fixed SiteChrome
**Context:** The Booking Outreach tab bar was placed at the very top of `/megs-playbook`. On mobile it collided with the global `SiteChrome` — the logo bleeds off the top-left to ~83px and the fixed "Menu" button occupies ~16–60px top-right (both mounted once in the root layout, `position: fixed`/absolute, above content). A 48px top pad put the pills under both. Existing routes never hit this because their headers start low (the playbook header used a 128px top pad).
**Lesson:** Any new UI anchored to the top of a route inherits an overlap with the persistent logo + mobile Menu button. Reserve top clearance on mobile (≥ ~96px / `--mc-space-8` clears the ~83px logo bleed and the Menu button) and drop it back on desktop (`@media (min-width:768px)`) where the centered column + top-right nav don't collide. Verify by reading the logo/Menu bounding rects against your element's top, not by eyeballing a screenshot.
**Trigger:** Adding a header, tab bar, toolbar, or banner at the top of any route in this repo. Check `getBoundingClientRect()` of the logo link and the Menu button at 390px before shipping.

## 2026-07-05 — One route, two callers: field-level guard beats two routes
**Context:** `PATCH /api/outreach/prospects/[id]` is called both by Meg's unguarded page (only "mark handled" → `needs_action`) and by the secret-guarded weekly run (status, cooling, cycle, etc.). Rather than split into two routes, one handler widens the accepted-field allowlist when a valid `x-outreach-secret` is present and 403s the page on any field outside `needs_action`.
**Lesson:** When two callers share a mutation route but differ only in *which fields* they may write, gate at the field level in one handler (allowlist keyed on the caller's auth), not by forking routes or trusting the client to send only permitted fields. The un-secreted caller can't widen its own scope, and there's one place to read the policy. Reject unknown fields explicitly (403 for the page, 400 for the machine) rather than silently dropping them.
**Trigger:** Any endpoint with a privileged and an unprivileged caller writing to the same resource. Extend the response/allowlist (studio learning #60, shared-route-extend-not-swap), never swap the shape per caller.

## 2026-07-05 — Shared single working tree + a parallel session's branch switch lands your commit on the wrong branch
**Context:** This repo runs several concurrent Claude/CC sessions against ONE primary checkout (plus CC Desktop worktrees). During a `/booking` fix I created `feature/booking-ui-form-refresh` off main, edited, `git commit`, `git push`. But the boot-scene session switched primary `HEAD` to `feature/shop-fix-boot-scene-motion` *between* my checkout and my commit — so my booking commit `30b2507` actually landed on top of the boot-scene branch (its parent was the boot session's `autoPort` commit), and my push shipped an **empty** booking branch (still at the old main tip). The HEAD reflog laid it bare: `checkout: booking → boot-scene`, then two boot commits, then my booking commit — all on the wrong branch. Later the boot session's own reset/merge (PR #19) silently discarded my misplaced copy.
**Lesson:** Never trust that primary `HEAD`/the current branch is still where you left it across tool calls when other sessions share the checkout — a concurrent branch switch is invisible and silently reparents your commit. Recover WITHOUT touching the primary tree: `git worktree add <tmp> <your-branch>`, `git cherry-pick <lost-sha>` (or `git rebase origin/main` for a conflicting merge), push from the worktree, `git worktree remove`. The lost commit is a real object (`git cat-file -t <sha>` / reflog) — cherry-pick replays only its diff onto the correct base. NEVER `git reset`/`git branch -f` a branch another session has checked out in the primary tree (that's the hazard that caused this) and NEVER hand-merge an append-log conflict — union each side's entries (studio #53). Verify the recovered branch shows ONLY your files (`git diff --stat origin/main..HEAD`) before force-pushing.
**Trigger:** Any commit/push in this repo while `git worktree list` shows other live sessions, or after any `Note: <file> was modified` reminder reverts files you just edited. Before committing, `git rev-parse --abbrev-ref HEAD` to confirm the branch; after, confirm the commit is on YOUR branch (`git branch --contains <sha>`) and that the push moved the intended ref, not an empty one. Studio-wide instances: #42 (confirm-main-before-session), #75 (concurrent-session-branch-supersession), #44 (match-worktree-to-work).

## 2026-07-24 — A macOS LaunchDaemon cannot read a Keychain-authenticated CLI's credentials, even while that user is logged in
**Context:** `agent/playbook-agent.mjs` shells out to `claude -p`, whose OAuth credentials live in the macOS **login Keychain** (confirmed: no `~/.claude/.credentials.json`, no on-disk credential file of any kind). Installed as a system LaunchDaemon via `agent/install-launchdaemon.sh`, every runtime check the installer makes passed — plist `root:wheel` 644, bootstrapped into the `system` domain, `launchctl list` showing the label, log file non-empty — and it still failed 100% of jobs: `claude` returned the literal string `Not logged in · Please run /login`, which fails `JSON.parse`, killing the job through both the first attempt and its one repair retry (~4.5s end to end). Re-queued against the per-user LaunchAgent (`gui/<uid>`), the identical job completed in 13.7s. The whole reason the 2026-07-13 ADR chose a LaunchDaemon was to survive a full log-out — a benefit that cannot exist here, because the credentials themselves are session-scoped.
**Lesson:** A LaunchDaemon runs in the system bootstrap context and has **no access to any user's login keychain, regardless of whether that user is currently logged in** — Keychain reachability follows the security session, not the unlock state. So for any background job that shells out to a CLI authenticated via Keychain (`claude`, `gh`, `aws`, most OAuth CLIs), a LaunchDaemon is not "a LaunchAgent that survives logout" — it is a job that can never authenticate. Use a LaunchAgent and accept that it runs only while the user is logged in, or authenticate the CLI by a means the system domain can actually read (env-var API key), which is usually the thing you were trying to avoid. Never pre-unlock a keychain from a root-readable script to work around this — that trades a working setup for a stored credential. Do not treat "an interactive login unlocks the Keychain for a later daemon" as true; it is not, and it reads plausibly enough to survive review (it did, in `agent/README.md`).
**Trigger:** Any time you reach for `/Library/LaunchDaemons` (or a systemd system unit, same class of bug with `gnome-keyring`/`kwallet`) for work that runs a CLI you logged into interactively. Before installing, ask what store holds that CLI's token — if the answer is the Keychain, the daemon is already broken. Diagnostic signature: jobs failing within seconds with an auth-refusal string where parseable output should be, while every launchd-level check reports healthy. Also: `launchctl list` + a non-empty log file do **not** prove a job works (studio #45, verify at the destination) — only a completed unit of real work does.

## 2026-07-24 — `claude -p` inherits the CLI's session model/effort; pin both explicitly in any automation
**Context:** The generation daemon spawned `claude -p --output-format stream-json --verbose` with no `--model`/`--effort`. Probing the `stream-json` init event showed the resolved model was **`claude-opus-5[1m]`**, while the interactive REPL header on the same machine displayed `Sonnet 5` — headless and interactive defaults differ, so the app had been silently running the most expensive model. Because the daemon runs on Meghan's own Pro subscription, its rate limits are shared with her personal Claude use, and an exhausted allowance yields unparseable output — which the daemon's retry semantics convert into a dead `error` job, not a graceful backoff. Pinning `--model sonnet --effort medium` kept all four exercised job kinds validating, except `storyboard` (the largest output) which failed `JSON.parse` on the first attempt and survived only on its single repair retry; at `--effort high` it passed first try twice and was **faster end to end** (41s, 48s) than the medium run that needed repair (89s).
**Lesson:** Never let a daemon or scheduled job inherit an interactive CLI's model/effort defaults. Pin them at the spawn site: it decouples the product's behaviour from whatever the human last typed in their own session (a `/model` change in chat should not retune a running app, and the coupling is silent in both directions), and it puts the model actually in use in the repo where review can see it. Verify the resolved model by reading the `stream-json` init event rather than trusting a REPL header. Tune effort **per task kind, not globally** — the kind emitting the largest structured output is the one that needs headroom, and paying its premium on every short job buys nothing. Counter-intuitively, a higher effort level can be cheaper *and* faster in wall-clock than a lower one that triggers a repair round trip, so measure end-to-end outcomes rather than assuming effort trades against latency.
**Trigger:** Any `claude -p`/SDK invocation inside a daemon, cron job, or CI step — pin `--model` and `--effort` at the point the spawn is written. Also any time a structured-output job starts failing validation on first attempt: check whether that kind outgrew its effort level before touching the prompt or the schema. Both of this pair are **studio-wide promotion candidates** (they change how any future daemon-plus-CLI project is built, not just this repo) — not promoted here, since that is a `studio-memory/learnings/` call.

## 2026-07-24 — A running daemon holds the code it started with; "the fix is merged" is not "the fix is live"
**Context:** PR #59 relaxed `onScreenText` to allow `""` in `agent/contracts.mjs` (merged 22:06 local). The LaunchAgent had started at 21:59:07 — Node had already resolved its ESM module graph, so the live daemon still enforced `.min(1)` and would still have rejected the output its own prompt asks for. All three of `agent/README.md`'s verification checks passed throughout (label loaded, log non-empty, jobs completing), because the jobs that happened to run had overlay text on every frame. The stale behaviour surfaces as `validation failed (attempt 1)` — i.e. it impersonates prompt/contract drift and sends the next reader to edit files that are already correct.
**Lesson:** For any long-lived process, the deployed artifact is the *process*, not the file. Verify by comparing the process's start time against the mtime of what it imports (`ps -o lstart -p <pid>` vs `ls -l agent/*.mjs`); if any source is newer, the running code is stale no matter what `git log` says. This is the same class as studio #45 (verify at the destination) with the destination being process memory — and note that "a real job completed" only proves the code is live if that job exercises the changed path. Restarting is part of landing the change: `launchctl kickstart -k gui/$(id -u)/<label>`.
**Trigger:** Any edit to `agent/*.mjs`, or to any file a resident daemon/server imports, in a repo where that process is already running. Check process age before concluding a merged fix is in effect — and before debugging a symptom the fix was supposed to remove.

## 2026-07-24 — `claude -p --output-format stream-json` emits one complete message unless you ask for partials
**Context:** The daemon's ~2s sync writes `{partial}` to the job row and flips it to `status='streaming'`. Sampled every 1s against a real 42s storyboard job, `output.partial` was never non-null and the `streaming` transition never happened. Direct instrumentation of the CLI showed why: without `--include-partial-messages`, the stream is `system/init` at 0.54s, silence until 9.52s, then the whole 1748-char message as a single `assistant` event, then `result`. The accumulator is empty for 88% of the run, so every tick returns early; the one write that lands arrives *after* the full text, a few hundred ms before `done`. Prior log lines that read as proof said the same thing with timestamps attached — `streaming` at 04:00:28.332 and `done` at 04:00:28.718, 386ms apart at the end of a 54s job. With the flag, `stream_event`/`content_block_delta` events flow continuously from 1.57s.
**Lesson:** "stream-json" names the *encoding*, not the delivery — it frames complete messages as JSON lines. Progressive token delivery needs `--include-partial-messages`, and a consumer that only handles `type === "assistant"` will see nothing until the end even with the flag on (it must also handle `type === "stream_event"`). When verifying any streaming feature, check the *timestamp gap* between the first partial and the terminal event, not merely that a partial/`streaming` state was ever observed — a status written 0.4s before completion is indistinguishable from working if you only grep for the word.
**Trigger:** Any code that consumes `claude -p --output-format stream-json` and reports progress, and any review of a claim that streaming "has been verified". Ask for the elapsed-time trace, not the presence of a log line.

## 2026-07-24 — An upstream quota refusal arrives as prose and gets classified as a schema failure
**Context:** After nine `claude -p` spawns in ~8.5 minutes, the CLI returned prose beginning `You've hit…` where JSON was expected. `validateOutput` reported `JSON.parse failed`, the one-shot repair retry fired **2.8 seconds later** into the same limit, and the job died as `Validation failed after repair retry: JSON.parse failed: Unexpected token 'Y', "You've hit"…`. The queued job behind it died identically in 6.1s, spending two more spawns against an endpoint that was already refusing. The limit was transient — a plain probe and then a full storyboard both succeeded later in the same session with no change.
**Lesson:** A structured-output pipeline treats every non-parseable reply as the model getting the format wrong, so an auth failure, a quota refusal, and a genuine schema miss all land in the same bucket with the same message — and the automatic repair retry, which exists for the third case, actively harms the first two by re-requesting immediately. Classify the raw reply *before* validating it: match known refusal strings, fail with a message naming the real cause, and don't spend a repair attempt on a condition no prompt can fix. Recoverability differs too — a schema miss is terminal for that job, a quota refusal wants a queue-level backoff, since it heals by itself. Watch for the tell: a validation error whose quoted fragment is English prose rather than malformed JSON.
**Trigger:** Any LLM call whose output is parsed/validated and retried on failure — especially one running on a personal subscription shared with a human's own usage, where exhaustion is normal rather than exceptional. Also any time a `JSON.parse failed` error quotes a capital letter and a word.

## 2026-07-24 — A fallback chain is not verified until you check what the producer actually sends
**Context:** The daemon's `titles` handler accepts three input shapes for `{{FRAMES}}` — `input.frames`, a JSON-parseable `input.context`, then a raw `input.context` string — with a comment explaining that the route-side schema was mid-reshaping. All three branches work (verified). But `jobInputSchemas.titles` in `generation.ts` has no `frames` field at all, and the route inserts `parsedInput.data`, so zod strips it: branch 1 is unreachable from the app. And the only call site, `handleFreshTitles` in `StoryboardResult.tsx:362`, sends `{ idea, previousTitles }` — no `context` either. So every real "Fresh titles" request falls through all three branches to the `[]` default, and the prompt reaches Claude reading `THE STORYBOARD FRAMES: []`.
**Lesson:** Defensive input handling written against an *anticipated* producer can be fully correct and still never run, and testing it by hand-crafting each input shape confirms the branches while proving nothing about production. Verify the chain from the producer end: find the actual call site, read what it constructs, and check which branch that lands in. A fallback whose default is a legal-but-empty value (`[]`, `{}`, `""`) fails silently — the job still validates and still returns plausible output, just built from less context than intended.
**Trigger:** Any `a ?? b ?? c ?? default` accepting multiple shapes of the same input, especially one whose comment cites a schema still being reshaped elsewhere. Grep for the call site before calling the fallback verified, and prefer a loud failure to an empty default when the input is supposed to be there.

## 2026-07-26 — Enabling token streaming means two accumulators, not one
**Context:** Turning on `--include-partial-messages` made the CLI emit `stream_event` deltas *and* still emit the complete `assistant` message at the end — both carrying the same text. The existing parser appended assistant text to a single buffer; naively adding the deltas to that same buffer would have doubled every reply, and the corruption would only appear in the *final* validated output, not in the progress display, so it would have read as the model emitting garbage.
**Lesson:** When a stream carries both incremental and terminal representations of the same content, keep them in separate accumulators and decide per consumer which to read: progress reads the deltas, correctness reads the complete message. Falling back (`assistantText || deltaText`) covers a process that dies before the terminal event. The general trap: enabling a "more detail" flag on an event stream usually *adds* events rather than replacing them, so any handler written against the old event set needs re-reading for double-counting, not just extending.
**Trigger:** Adding a partial/verbose/delta flag to any event stream that an existing parser consumes — SSE, `stream-json`, websocket protocols. Diff the event types before and after, and check whether the new ones duplicate content the old ones already delivered.

## 2026-07-26 — Classify a failure by whether waiting fixes it, then pick the retry
**Context:** The daemon treated every non-parseable reply identically: one repair retry, then dead. That bucket held three unlike things — a malformed model reply (retry helps), an exhausted quota (retry actively harms; waiting helps), and a logged-out CLI (nothing but a human helps). Splitting them produced three different behaviours from one detector: repair retry, requeue-with-escalating-cooldown, and immediate loud failure.
**Lesson:** "How many times should this retry?" is the wrong first question. Ask what would have to change for the next attempt to succeed — nothing (retry now), time (back off and requeue), or a human (fail loudly and say what to do). Failure paths that skip this collapse to one policy and get all but one case wrong, and the damage is worst for the transient case, where an immediate retry both fails and consumes the scarce resource that caused the failure. Bound the waiting case anyway, and prefer forgetting the bound on restart over persisting it — the operator restarting the daemon is usually the operator who just fixed the cause.
**Trigger:** Any `catch` or validation failure that leads to a retry decision. Enumerate the distinct causes that can land there before choosing the policy — and be conservative in the detector, since misclassifying a retryable failure as permanent is the expensive direction.

## 2026-07-26 — The strongest preference signal is the option that was rejected, not the one that was kept
**Context:** `storyboards` recorded both the title options offered and the one Meghan chose, but nothing read the column. The obvious use is "here are titles she liked"; the better one turned out to be `{chose, passedOver}` — because every entry in `passedOver` was generated by the same model, judged good enough to present, and declined anyway. Injecting that pair flipped every option in an A/B test to her actual register, and the model's own rationales cited the contrast ("the same way her three prior picks did").
**Lesson:** When a UI makes someone pick one of N generated options, persist the whole choice — the winner *and* the losers — not just the winner. A list of accepted items reads as "things that are good"; a choice between comparable candidates reads as "what distinguishes good from chosen", which is the part a prompt cannot infer from published output. This is nearly free wherever a product already generates options: the losers are in memory at selection time and cost one column to keep. Pair it with an explicit "if this list is empty, ignore it" instruction, or the model will manufacture a pattern from two data points.
**Trigger:** Any feature that generates several options and records which one the user took — titles, captions, suggested replies, template pickers. Check whether the rejected candidates are being dropped on the floor, and whether anything reads the accepted one back.

## 2026-07-28 — A PostgREST list read has two ceilings, and the id-list one arrives first
**Context:** Fixing the 1000-row `.select()` cap (studio learning #84) on `/api/outreach/run-state` meant paging two queries. The second read — every inbound message for every actionable prospect — filters with `.in("prospect_id", ids)`, where `ids` is every actionable prospect. Paging fixes how many rows come *back*; it does nothing about how the request goes *out*. PostgREST takes filters in the query string, so that id list is serialised into the URL: ~39 bytes per quoted uuid, which puts a few hundred prospects near the common 8KB request-line limit. The row cap bites at 1000 rows of output; the URL cap bites at roughly 200 ids of input, and both live in the same one-line query.
**Lesson:** Paging and chunking solve different halves of the same scaling problem and neither implies the other — a fully paged query can still 414 on its own filter. When a read is bounded by a set of ids you fetched from another table, size *both* directions: page the response, chunk the id list. The failure modes differ usefully, too — truncation is silent and corrupts results, while a 414 is loud and fails the request — so the row cap is the more dangerous one and the URL cap is the one you can afford to discover in production. Fix both while the query is open anyway.
**Trigger:** Any `.in(col, ids)` where `ids` comes from a prior query rather than a fixed literal — especially on a machine/automation route, where a 414 lands in a log nobody reads. Ask what the id count is at 10× today's data, not today's.
